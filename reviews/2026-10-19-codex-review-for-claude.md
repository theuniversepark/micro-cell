## 1. PUBLIC=1 가격 마스킹이 일부 페이지에만 적용됨

**관련 코드** — 기준 커밋의 행 번호:

## 2. 복호화 도중 접으면 재열람 시 암호 재확인이 누락됨

**영향:** 최신 커밋의 “열 때마다 암호 재확인” 동작이 비동기 처리 완료 순서에 따라 지켜지지 않음. 최초 올바른 암호 제출 없이 암호화를 해제할 수 있다는 의미는 아님.

**관련 코드:**

- `build_ocs_sim.py:983-995`: 접을 때 현재 이미지·입력값을 초기화함.
- `build_ocs_sim.py:1004-1014`: 진행 중인 복호화가 끝나면 현재 펼침 상태나 요청 유효성을 확인하지 않고 이미지와 폼 상태를 변경함.

**재현 순서:**

1. 견적서 원본을 펼침.
2. 올바른 암호를 제출하여 비동기 복호화를 시작.
3. 완료 전에 견적서 원본을 접음.
4. 이전 요청의 복호화가 완료됨.
5. 다시 펼침. 암호가 비어 있어도 이미지가 표시됨.

**검증 방식:** 실제 생성된 JavaScript를 Node VM에서 실행하고 DOM과 WebCrypto 성공 응답을 최소 모의함. 복호화 Promise의 완료 시점을 수동 제어하여 닫기 이후 완료되게 했음. 실제 비밀번호·견적 이미지 복호화는 하지 않았으며 실제 브라우저에서의 타이밍 테스트는 미실시.

```text
after close during decryption:
  panelHidden=true, imageHidden=true, imgSrc=null, passwordCleared=true
reopened without submitting a password:
  panelHidden=false, imageHidden=false, imgSrc=blob:synthetic-test-image,
  formHidden=true, passwordEmpty=true
REAUTH_RACE_REPRODUCED=true
```

**수정 방향:** 제출마다 요청 식별자/세대 번호를 부여하고, 접을 때 무효화. 성공·실패 콜백 모두 현재 요청이며 패널이 열려 있을 때만 UI를 갱신하도록 처리. 중복 제출, 늦게 끝난 이전 요청, Blob URL 정리도 같은 수명주기로 관리.

**완료 기준:**

- 일반 성공 → 접기 → 다시 열기: 암호 입력이 다시 필요함.
- 제출 → 완료 전 접기 → 완료 → 다시 열기: 이미지가 없고 재입력이 필요함.
- 제출 → 접기 → 즉시 다시 열기 → 이전 요청 완료: 이전 결과가 새 패널에 적용되지 않음.
- 늦은 실패 콜백이 닫힌 패널의 메시지·포커스를 변경하지 않음.
- FMS·Adaptive·QMS 3개 생성 페이지에 동일하게 반영됨.

## 3. 구성품 표의 소계·합계 행 열 수와 금액 위치가 잘못됨

**영향:** 3개 OCS 시뮬레이션 페이지에서 소계·합계 금액이 ‘금액’이 아닌 ‘지침 점검’ 열 위치에 들어감. Word도 불필요한 열을 포함한 표로 생성됨.

**관련 코드:**

- `build_ocs_sim.py:443`: 그룹 행은 `colspan=7 + 금액 1 + colspan=3`, 총 11열.
- `build_ocs_sim.py:475-477`: 합계 행은 `colspan=7 + 금액 1 + colspan=2`, 총 10열.
- `build_ocs_sim.py:480-481`: 실제 표 제목은 9열이며 금액은 7번째 열.
- `export_docs.py:281`: Word 변환 시 행의 최대 열 수를 사용하여 11열로 확장됨.

**확인된 결과:**

- FMS·Adaptive·QMS 모두 제목 9열, 불일치 행 각 8개(항목 그룹 5개 + 합계 3개).
- 해당 행의 금액 셀은 8번째 열이며 제목은 ‘지침 점검’.
- 저장된 `docs/ocs_sim_{fms,adaptive,qms}.docx`의 해당 표 `w:tblGrid`는 모두 11열.
- 분류별 접기 행 `tr.cat`는 이미 9열이므로 같이 잘못 변경하지 않도록 주의.

**수정 방향:** 기존 9열 구조를 유지할 경우 그룹/합계의 제목 영역을 6열, 금액 1열, 나머지 2열로 맞추면 금액이 7번째 열에 정렬됨. 생성기 수정 후 HTML·PDF·Word를 재생성.

**완료 기준:**

- 해당 표의 모든 실제 데이터 행에서 `colspan`을 합한 열 수가 9.
- 모든 소계·합계 금액이 7번째 ‘금액’ 열에 위치.
- Word 해당 표의 격자가 9열이며 PDF에서도 표 정렬이 맞음.
- 기본 접힘, 개별/전체 펼침·접기, 키보드 조작, 인쇄 시 전체 행 표시가 유지됨.

## 4. 문서 생성 실패 시 이전 PDF가 성공 결과처럼 남을 수 있음

**영향:** HTML만 갱신되고 PDF는 이전 파일인 상태가 생길 수 있으며, 파일이 존재한다는 이유로 성공처럼 출력됨. Word 도면 이미지 생성 실패도 누락으로 이어질 수 있음.

**관련 코드:**

- `export_docs.py:31-33`: Chrome 실행에 `check=False`, 반환 코드 미검사, 오류 출력 폐기.
- `export_docs.py:36-37`: PDF 생성 성공을 검증하지 않음.
- `export_docs.py:49-50, 238-239`: 그림 파일이 없으면 `None`을 반환하고 Word 그림 삽입을 건너뜀.
- `export_docs.py:423`: 새로 생성됐는지와 관계없이 `os.path.exists`만 성공 지표로 출력.
- `build.sh:11`: 내보내기 실패를 `echo`로 처리하여 전체 빌드는 성공 종료할 수 있음.

**검증 방식:** 소스에서 `chrome()`과 `pdf()` 함수를 추출하여 실행. subprocess를 종료 코드 1의 실패 응답으로 모의하고, 이전 PDF를 뜻하는 파일을 임시 폴더에 미리 생성.

```text
browser_exit=1
exception_propagated=false
existing_file_still_reported_success=true
stale_bytes_unchanged=true
```

이는 실패 처리의 격리 검증이며 실제 Chrome 장애나 현재 PDF의 내용 불일치를 확인했다는 뜻은 아님.

**수정 방향:** 종료 코드·타임아웃·출력 생성 여부를 검사하고 실패를 상위 빌드에 전달. 임시 경로에서 새 문서를 생성·검증한 뒤 최종 파일을 교체하면 이전 파일을 새 성공 결과로 오인하는 문제를 막을 수 있음. HTML만 만드는 선택 모드를 유지한다면 문서 빌드와 성공 상태를 명확히 구분.

**완료 기준:**

- Chrome 종료 코드 오류·타임아웃·출력 미생성 시 실패가 명확히 보고됨.
- 이전 PDF가 있어도 새 내보내기 성공으로 표시하지 않음.
- Word의 필수 도면 생성 실패를 조용히 무시하지 않음.
- 정상 환경에서는 5개 상세 페이지의 PDF·Word를 모두 갱신하고 성공을 확인.
